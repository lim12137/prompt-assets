# 2026-05-01 提示词管理与样例清理设计稿

## 1. 目标与范围

本文用于固化已确认的“提示词管理与样例清理”方案，作为后续产品、研发、测试与验收的统一基线。本文只定义设计，不包含代码实现。

本次设计目标有四个：

1. 清理当前真实库中的样例提示词，避免演示数据与正式资产混用。
2. 在不破坏现有测试基线的前提下，补齐后台提示词管理能力。
3. 统一提示词生命周期、分类规则与后台交互语义。
4. 明确实施顺序、权限边界、审计要求、测试迁移要求与主要风险。

本次纳入范围：

- 真实库样例清理策略
- 提示词生命周期模型
- 多分类与主分类规则
- 后台管理交互设计
- 前台分类筛选交互规则
- 权限、审计、风险与实施顺序

本次不纳入范围：

- `fixture`/`seed` 基线调整
- 新一轮样例内容重写
- 前台大改版
- 分类层级化、智能推荐、批量自动归类
- `draft`、`submission` 现有流程改造

明确约束：

- 先删真实库样例，再做后台管理能力。
- 不改 `fixture`/`seed` 基线。
- `draft` 和 `submission` 流程本次明确不动，本次只处理分类与清理规则。

## 2. 当前基线与问题

当前仓库已经具备提示词发布、归档、多分类与后台分类管理的基础能力，`published`、`archived` 等状态语义也已在现有设计与实现中出现。但真实数据库中仍可能存在早期样例、演示数据或占位内容，这会带来三个直接问题：

1. 正式使用环境中真实资产与样例资产混杂，影响检索与判断。
2. 后续如果直接补后台管理，会把“清脏数据”和“做治理能力”耦合在一起，增加验收噪声。
3. 测试链路依赖的 `fixture`/`seed` 与真实库运行数据承担不同职责，若混改会破坏既有回归基线。

因此，本次方案把“真实库样例清理”视为独立的先置治理动作，而不是后台能力的一部分。

## 3. 初始样例清理策略

### 3.1 清理对象

本次“样例”仅指真实数据库中的非正式提示词资产，包括但不限于：

- 演示用途的占位提示词
- 为联调、截图、验收临时写入的内容
- 已确认不应继续对用户展示的历史样例

不属于本次清理对象：

- `tests/fixtures/prompts.ts` 中的测试样例
- `packages/db/src/seed.ts` 写入的测试或开发基线数据
- 自动化测试依赖的任何 `fixture`/`seed` 数据结构

### 3.2 清理原则

1. 只清真实库，不碰测试基线。
2. 先人工确认清单，再执行删除。
3. 首批真实库清理不要求快照、回滚方案或审批记录。
4. 清理动作仍需保留最小必要的执行记录，便于事后核对。
5. 清理以“彻底删除”为目标，不通过新增复杂状态规避。

### 3.3 清理判定口径

进入首批清理清单的提示词，至少满足以下之一：

- 明确标记为演示、样例、测试、占位
- 业务已确认不需要保留
- 没有正式使用价值且仅用于历史联调

对边界不清的内容，默认先不删，转人工复核。

### 3.4 首批执行方式

首批不依赖新后台功能，不等待新页面完成。执行方式如下：

1. 从真实库导出待清理提示词清单。
2. 由业务/产品确认“可删”范围。
3. 按确认清单执行真实库彻底删除。
4. 记录删除对象、执行人、执行时间、删除原因，形成一次性审计记录。

### 3.5 与测试基线隔离

本次必须明确区分两类数据：

- 真实库运行数据：服务当前实际使用，允许按业务决策删除。
- `fixture`/`seed` 基线数据：服务开发、测试、回归，不因真实库清理而调整。

结论：首批样例清理不触发 `fixture`/`seed` 改动，也不以“同步删测试样例”为完成条件。

## 4. 生命周期模型

本次确认提示词生命周期中，现存流程状态与本次治理范围需要明确拆开。

现有流程状态继续存在：

- `draft`
- `submission`

但本次不调整这两条流程，也不把它们纳入首批后台治理与样例清理规则。本次只确认以下业务结果状态与删除规则：

- `published`
- `archived`
- 彻底删除

### 4.1 `published`

含义：

- 对前台可见
- 参与搜索、筛选、详情查看与复制
- 视为当前正式资产

适用场景：

- 已审核通过并正式发布
- 仍需对用户持续提供使用

### 4.2 `archived`

含义：

- 不再作为前台默认可见资产
- 仍保留记录，用于后台治理、审计与必要回看
- 不等同于删除

适用场景：

- 内容过时但需要保留历史痕迹
- 被新资产替代但暂不适合物理清除
- 有审计保留价值

### 4.3 彻底删除

含义：

- 从真实业务库中移除，不再作为业务资产保留
- 不是前台隐藏，也不是后台归档
- 用于明确无保留价值的样例或脏数据

适用场景：

- 首批真实库样例清理
- 明确误导性、临时性、占位性内容
- 经确认无须继续保留的非正式资产

### 4.4 生命周期转换规则

允许的核心转换如下：

1. `draft`、`submission` 按既有流程继续流转，本次不改
2. 新建并发布后进入 `published`
3. `published` 可转为 `archived`
4. `archived` 可重新恢复为 `published`
5. `published` 或 `archived` 在满足权限与确认条件时可被彻底删除

规则补充：

- `draft` 继续存在，但不纳入本次后台治理口径，不作为本轮清理对象定义基础。
- `submission` 继续存在，但不在本次设计中新增或修改流转规则。
- “彻底删除”是终态，不提供业务层恢复承诺。
- 首批样例清理优先直接走“彻底删除”，不要求先转 `archived`。
- 对正式运营资产，默认优先 `archived`，删除需更高确认门槛。
- 一旦执行彻底删除，关联的版本、投稿、评分、点赞、交互等历史允许一并物理删除，不要求为首批清理保留业务历史。

## 5. 多分类与主分类规则

### 5.1 多分类基线

延续现有多分类存储设计，一个提示词可属于多个分类；但本次明确区分“主分类权威字段”和“补充多分类关系”。

### 5.2 主分类定义

虽然一个提示词可挂多个分类，但后台需要维护唯一主分类，用于：

- 列表默认展示口径
- 后台排序与运营视图聚合
- 导入、审计与后续统计的一致口径

规则：

1. `prompts.category_id` 是主分类唯一权威字段，也是展示、统计、治理、迁移时的真源。
2. 每个提示词必须且只能有一个主分类。
3. 主分类必须属于该提示词已关联分类集合。
4. `prompt_categories` 仅作为多分类补充关系，不能与 `prompts.category_id` 打架。
5. 若仅有一个分类，该分类自动成为主分类，同时写回 `prompts.category_id`。

### 5.3 多分类规则

1. 一个提示词至少有一个分类。
2. 可配置多个辅助分类。
3. 主分类用于单值展示，辅助分类用于补充检索与归属表达。
4. `prompt_categories` 中必须包含主分类对应关系，避免主分类脱离关联集合。
5. 若 `prompt_categories` 与 `prompts.category_id` 不一致，以 `prompts.category_id` 为准，并在治理或迁移时补齐关系表。

### 5.4 删除分类时的处理

1. 删除某个分类时，先解除提示词与该分类的关联。
2. 若该分类不是主分类，则只移除该关联。
3. 若该分类是主分类且仍有其他分类，必须同步改写 `prompts.category_id` 为新的主分类，并补齐对应关系。
4. 若删除后提示词没有任何分类，则自动归入系统待分类，并把系统待分类写入 `prompts.category_id`。

### 5.5 系统待分类规则

延续现有系统分类约束：

- 系统待分类只作为兜底归类目标
- 默认不作为普通人工选择项
- 删除分类导致零分类时自动挂入
- 管理员为提示词补上正式分类后，系统待分类必须自动移除
- 若当前主分类是系统待分类，管理员一旦指定正式分类，`prompts.category_id` 必须切换为该正式分类

### 5.6 待分类退出规则

待分类退出必须是自动规则，不允许依赖人工额外清理：

1. 当提示词当前仅挂系统待分类时，管理员新增任一正式分类并保存，系统待分类自动移除。
2. 当提示词同时挂系统待分类和正式分类时，只要管理员确认正式主分类，系统待分类自动移除。
3. 自动移除后，`prompts.category_id` 必须指向已确认的正式主分类。
4. 后台界面不提供“保留待分类并同时视为已正式分类”的状态。

## 6. 后台交互设计

### 6.1 后台目标

后台新增或收敛的不是“样例清理页面”，而是正式的提示词治理能力。样例清理属于先置的一次性数据治理动作，后台则负责长期维护。

### 6.2 列表页

后台提示词列表建议提供以下字段与筛选：

- 标题
- `slug`
- 生命周期状态
- 主分类
- 其他分类
- 最近更新时间
- 创建人或最近操作人

筛选项建议包括：

- 状态筛选：`published`、`archived`
- 分类筛选
- 关键词搜索
- 是否仅看待分类

列表与筛选口径补充：

- 后台分类展示与筛选默认读取 `prompts.category_id` 作为主分类真源。
- 其他分类仅作为补充标签展示，不得反向覆盖主分类判断。

### 6.3 提示词编辑页

编辑页需要支持：

- 修改标题、摘要、正文等既有信息
- 维护多分类
- 显式指定主分类
- 执行归档或恢复发布

交互要求：

1. 先选分类，再选主分类。
2. 主分类下拉列表只展示当前已选分类。
3. 分类改动后若主分类失效，界面必须要求重新指定。
4. 若原先存在系统待分类，管理员补上正式分类并保存后，系统待分类自动移除，不再要求额外手动取消。

### 6.4 删除交互

后台删除为高风险操作，需独立于归档按钮。

删除流程建议：

1. 点击“彻底删除”
2. 弹出确认框
3. 明确展示提示词标题、`slug`、当前状态、分类信息
4. 明确提示“删除后不可恢复”
5. 二次确认后执行删除并写审计日志

删除结果约束：

- 允许级联物理删除该提示词关联的版本、投稿、评分、点赞、交互等历史数据。
- 本次不要求为首批清理额外保留业务层回滚能力。

### 6.5 归档交互

`archived` 与删除必须分开：

- 归档：用于从前台下线但保留资产记录
- 删除：用于彻底清除不再保留的资产

因此后台列表和详情页都应同时提供“归档/恢复发布”和“彻底删除”两类操作，且视觉层级明显区分。

### 6.6 前台分类筛选交互规则

首页分类器本次明确采用“切换单选”规则，而不是多选：

1. 默认无分类筛选。
2. 点击某个分类后，进入该分类筛选状态。
3. 已选中某分类时，再点击另一个分类，直接切换到新分类。
4. 已选中某分类时，再点击当前分类，取消分类筛选，回到默认状态。
5. 前台首页分类器不提供多选累积，也不采用 OR 叠加交互。

说明：

- 这里约束的是首页分类器交互，不改变底层多分类存储设计。
- 前台展示命中规则仍以提示词属于该分类即可展示。

## 7. 权限设计

### 7.1 角色边界

普通用户：

- 浏览与使用 `published` 提示词
- 不具备后台治理权限

管理员：

- 查看后台提示词列表
- 编辑分类与主分类
- 执行发布、归档、恢复发布
- 执行彻底删除
- 查看相关审计记录

### 7.2 删除权限

彻底删除必须只允许管理员执行，且建议保留更严格约束：

- 首批样例清理由少数指定管理员执行
- 正式运营后，删除仅用于确认无保留价值的数据

### 7.3 前后台可见性

- 前台仅展示 `published`
- `archived` 与已删除内容不在前台出现
- 后台可查看 `published`、`archived`
- 已彻底删除内容不再作为业务记录参与后台列表，但审计日志保留其删除痕迹

## 8. 审计要求

以下动作必须写审计日志：

1. 首批真实库样例清理
2. 提示词归档
3. 提示词恢复发布
4. 提示词彻底删除
5. 主分类变更
6. 分类关联变更

每条审计至少记录：

- 操作人
- 操作时间
- 操作对象
- 操作类型
- 变更前摘要
- 变更后摘要
- 执行结果
- 删除或变更原因

对于首批样例清理，仅要求形成一次文档化执行记录用于核对；本次不把审批流、快照或正式回滚预案列为必备交付物。

## 9. 风险与控制

### 9.1 误删真实资产风险

风险：

- 把仍有业务价值的提示词当作样例删掉

控制：

- 首批清理先导出清单
- 先人工确认再删除
- 清理范围从“明确样例”开始，不做模糊扩删

### 9.2 把归档与删除混用

风险：

- 后台使用者把“下线”误当“删除”，导致资产不可恢复

控制：

- 后台显式区分“归档”和“彻底删除”
- 删除确认文案必须强调不可恢复

### 9.3 分类与主分类失配

风险：

- 多分类调整后主分类指向不存在的关联分类

控制：

- 后端强校验主分类必须属于关联分类
- `prompts.category_id` 作为唯一真源
- 前端分类变更时强制重新选择有效主分类
- 迁移或修复时自动补齐 `prompt_categories` 中的主分类关系

### 9.4 测试基线被误改

风险：

- 把真实库清理动作扩散到 `fixture`/`seed`

控制：

- 方案层面明确禁止
- 本轮仅做真实库治理，不把测试样例同步纳入清理范围

### 9.5 待分类长期滞留风险

风险：

- 管理员已补正式分类，但系统待分类未退出，导致前后台语义混乱

控制：

- 设计上规定补正式分类后自动移除系统待分类
- 保存时同时校验并修正 `prompts.category_id` 与补充分类关系

## 10. 实现顺序

本次顺序必须固定，不做并行倒置：

1. 确认真实库待清理样例清单
2. 执行真实库样例彻底删除，并留存审计记录
3. 验证前台与真实库当前正式数据口径稳定
4. 再进入后台提示词管理能力建设
5. 在后台补齐生命周期操作、多分类主分类维护、删除确认与审计展示

这里再次明确：

- 先删真实库样例，再做后台管理能力。
- 不改 `fixture`/`seed` 基线。
- 不改 `draft`、`submission` 既有流程。

## 11. 迁移与测试要求

本节用于把“需要测试/需要迁移”收敛成可执行口径，后续实现与验收必须按此落地。

### 11.1 数据迁移要求

若后续实现涉及分类数据修正，迁移口径必须满足：

1. 逐条扫描提示词，检查 `prompts.category_id` 是否为空、是否指向有效分类、是否已存在于该提示词的补充分类关系中。
2. 若 `prompts.category_id` 有值但关系表缺失，则自动补齐对应主分类关系。
3. 若提示词无任何分类，则挂入系统待分类，并将 `prompts.category_id` 写为系统待分类。
4. 若提示词同时存在系统待分类和正式分类，则以正式主分类为准，并移除系统待分类。
5. 迁移脚本执行完成后，输出结果至少包含：扫描总数、补齐主分类关系数、自动挂入待分类数、自动移除待分类数、异常数。

### 11.2 测试要求

后续实现验收至少覆盖以下可执行场景：

1. 新增或编辑提示词时，主分类最终写入 `prompts.category_id`，且关系表包含同一分类。
2. 删除非主分类时，仅移除补充关系，不改主分类。
3. 删除主分类且仍有其他分类时，必须切换新的主分类并同步更新关系表。
4. 删除最后一个正式分类时，必须自动进入系统待分类。
5. 管理员补正式分类后，系统待分类必须自动移除。
6. 首页分类器验证三态交互：默认无筛选、点击分类进入单选、点击当前分类取消、点击其他分类切换。
7. 彻底删除提示词后，关联版本、投稿、评分、点赞、交互等历史允许一并物理删除，且前后台都不可再查询该业务对象。
8. `draft`、`submission` 既有流程在本轮实现中不得出现行为回归。

### 11.3 测试产物要求

并发测试或专项测试结论必须落盘到 `docs` 目录下的测试报告，报告至少包含：

1. 测试时间
2. 测试环境
3. 测试命令

## 13. 核心结论

本次不是“顺手在后台里加删除按钮”，而是一次顺序明确的数据治理与后台治理拆分：

1. `draft` 和 `submission` 流程本次不动，本次只处理分类与清理规则。
2. 首先清理真实库样例，直接做彻底删除；首批不要求快照、回滚方案或审批记录。
3. 生命周期治理聚焦 `published`、`archived`、彻底删除三类结果，且允许删除时级联物理清除相关历史。
4. 主分类唯一真源固定为 `prompts.category_id`，`prompt_categories` 仅作补充，不能与主分类冲突。
5. 系统待分类仅作兜底，管理员补正式分类后必须自动退出待分类。
6. 首页分类器采用切换单选：点分类选中，点其他分类切换，点当前分类取消。
7. 后台能力在样例清理之后建设，重点是长期治理，而不是承担首批清库动作。
8. 整个过程不修改 `fixture`/`seed` 基线，确保测试与回归口径稳定。
