# 2026-05-01 提示词管理与样例清理设计稿

## 1. 目标与范围

本文用于固化已确认的“提示词管理与样例清理”方案，作为后续产品、研发、测试与验收的统一基线。本文只定义设计，不包含代码实现。

本次设计目标有四个：

1. 清理当前真实库中的样例提示词，避免演示数据与正式资产混用。
2. 在不破坏现有测试基线的前提下，补齐后台提示词管理能力。
3. 统一提示词生命周期、分类规则与后台交互语义。
4. 明确实施顺序、权限边界、审计要求与主要风险。

本次纳入范围：

- 真实库样例清理策略
- 提示词生命周期模型
- 多分类与主分类规则
- 后台管理交互设计
- 权限、审计、风险与实施顺序

本次不纳入范围：

- `fixture`/`seed` 基线调整
- 新一轮样例内容重写
- 前台大改版
- 分类层级化、智能推荐、批量自动归类

明确约束：

- 先删真实库样例，再做后台管理能力。
- 不改 `fixture`/`seed` 基线。

## 2. 当前基线与问题

当前仓库已经具备提示词发布、归档、多分类与后台分类管理的基础能力，`published`、`archived` 等状态语义也已在现有设计与实现中出现。但真实数据库中仍可能存在早期样例、演示数据或占位内容，这会带来三个直接问题：

1. 正式使用环境中真实资产与样例资产混杂，影响检索与判断。
2. 后续如果直接补后台管理，会把“清脏数据”和“做治理能力”耦合在一起，增加验收噪声。
3. 测试链路依赖的 `fixture`/`seed` 与真实库运行数据承担不同职责，若混改会破坏既有回归基线。

因此，本次方案把“真实库样例清理”视为独立的先置治理动作，而不是后台能力的一部分。

## 3. 初始样例清理策略

### 3.1 清理对象

本次“样例”仅指真实数据库中的非正式提示词资产，包括但不限于：

- 演示用途的占位提示词
- 为联调、截图、验收临时写入的内容
- 已确认不应继续对用户展示的历史样例

不属于本次清理对象：

- `tests/fixtures/prompts.ts` 中的测试样例
- `packages/db/src/seed.ts` 写入的测试或开发基线数据
- 自动化测试依赖的任何 `fixture`/`seed` 数据结构

### 3.2 清理原则

1. 只清真实库，不碰测试基线。
2. 先人工确认清单，再执行删除。
3. 清理动作要可审计、可追溯、可回看。
4. 清理以“彻底删除”为目标，不通过新增复杂状态规避。

### 3.3 清理判定口径

进入首批清理清单的提示词，至少满足以下之一：

- 明确标记为演示、样例、测试、占位
- 业务已确认不需要保留
- 没有正式使用价值且仅用于历史联调

对边界不清的内容，默认先不删，转人工复核。

### 3.4 首批执行方式

首批不依赖新后台功能，不等待新页面完成。执行方式如下：

1. 从真实库导出待清理提示词清单。
2. 由业务/产品确认“可删”范围。
3. 按确认清单执行真实库彻底删除。
4. 记录删除对象、执行人、执行时间、删除原因，形成一次性审计记录。

### 3.5 与测试基线隔离

本次必须明确区分两类数据：

- 真实库运行数据：服务当前实际使用，允许按业务决策删除。
- `fixture`/`seed` 基线数据：服务开发、测试、回归，不因真实库清理而调整。

结论：首批样例清理不触发 `fixture`/`seed` 改动，也不以“同步删测试样例”为完成条件。

## 4. 生命周期模型

本次确认提示词生命周期采用三种业务结果：

- `published`
- `archived`
- 彻底删除

### 4.1 `published`

含义：

- 对前台可见
- 参与搜索、筛选、详情查看与复制
- 视为当前正式资产

适用场景：

- 已审核通过并正式发布
- 仍需对用户持续提供使用

### 4.2 `archived`

含义：

- 不再作为前台默认可见资产
- 仍保留记录，用于后台治理、审计与必要回看
- 不等同于删除

适用场景：

- 内容过时但需要保留历史痕迹
- 被新资产替代但暂不适合物理清除
- 有审计保留价值

### 4.3 彻底删除

含义：

- 从真实业务库中移除，不再作为业务资产保留
- 不是前台隐藏，也不是后台归档
- 用于明确无保留价值的样例或脏数据

适用场景：

- 首批真实库样例清理
- 明确误导性、临时性、占位性内容
- 经确认无须继续保留的非正式资产

### 4.4 生命周期转换规则

允许的核心转换如下：

1. 新建并发布后进入 `published`
2. `published` 可转为 `archived`
3. `archived` 可重新恢复为 `published`
4. `published` 或 `archived` 在满足权限与确认条件时可被彻底删除

规则补充：

- “彻底删除”是终态，不提供业务层恢复承诺。
- 首批样例清理优先直接走“彻底删除”，不要求先转 `archived`。
- 对正式运营资产，默认优先 `archived`，删除需更高确认门槛。

## 5. 多分类与主分类规则

### 5.1 多分类基线

延续现有多分类设计，一个提示词可属于多个分类，前台筛选保持多选 OR 逻辑。

### 5.2 主分类定义

虽然一个提示词可挂多个分类，但后台需要维护唯一主分类，用于：

- 列表默认展示口径
- 后台排序与运营视图聚合
- 导入、审计与后续统计的一致口径

规则：

1. 每个提示词必须且只能有一个主分类。
2. 主分类必须属于该提示词已关联分类集合。
3. 若仅有一个分类，该分类自动成为主分类。

### 5.3 多分类规则

1. 一个提示词至少有一个分类。
2. 可配置多个辅助分类。
3. 主分类用于单值展示，辅助分类用于补充检索与归属表达。
4. 前台筛选按“任一分类命中即可展示”处理。

### 5.4 删除分类时的处理

1. 删除某个分类时，先解除提示词与该分类的关联。
2. 若该分类不是主分类，则只移除该关联。
3. 若该分类是主分类且仍有其他分类，必须改选新的主分类。
4. 若删除后提示词没有任何分类，则自动归入系统待分类，并把系统待分类设为主分类。

### 5.5 系统待分类规则

延续现有系统分类约束：

- 系统待分类只作为兜底归类目标
- 默认不作为普通人工选择项
- 删除分类导致零分类时自动挂入

## 6. 后台交互设计

### 6.1 后台目标

后台新增或收敛的不是“样例清理页面”，而是正式的提示词治理能力。样例清理属于先置的一次性数据治理动作，后台则负责长期维护。

### 6.2 列表页

后台提示词列表建议提供以下字段与筛选：

- 标题
- `slug`
- 生命周期状态
- 主分类
- 其他分类
- 最近更新时间
- 创建人或最近操作人

筛选项建议包括：

- 状态筛选：`published`、`archived`
- 分类筛选
- 关键词搜索
- 是否仅看待分类

### 6.3 提示词编辑页

编辑页需要支持：

- 修改标题、摘要、正文等既有信息
- 维护多分类
- 显式指定主分类
- 执行归档或恢复发布

交互要求：

1. 先选分类，再选主分类。
2. 主分类下拉列表只展示当前已选分类。
3. 分类改动后若主分类失效，界面必须要求重新指定。

### 6.4 删除交互

后台删除为高风险操作，需独立于归档按钮。

删除流程建议：

1. 点击“彻底删除”
2. 弹出确认框
3. 明确展示提示词标题、`slug`、当前状态、分类信息
4. 明确提示“删除后不可恢复”
5. 二次确认后执行删除并写审计日志

### 6.5 归档交互

`archived` 与删除必须分开：

- 归档：用于从前台下线但保留资产记录
- 删除：用于彻底清除不再保留的资产

因此后台列表和详情页都应同时提供“归档/恢复发布”和“彻底删除”两类操作，且视觉层级明显区分。

## 7. 权限设计

### 7.1 角色边界

普通用户：

- 浏览与使用 `published` 提示词
- 不具备后台治理权限

管理员：

- 查看后台提示词列表
- 编辑分类与主分类
- 执行发布、归档、恢复发布
- 执行彻底删除
- 查看相关审计记录

### 7.2 删除权限

彻底删除必须只允许管理员执行，且建议保留更严格约束：

- 首批样例清理由少数指定管理员执行
- 正式运营后，删除仅用于确认无保留价值的数据

### 7.3 前后台可见性

- 前台仅展示 `published`
- `archived` 与已删除内容不在前台出现
- 后台可查看 `published`、`archived`
- 已彻底删除内容不再作为业务记录参与后台列表，但审计日志保留其删除痕迹

## 8. 审计要求

以下动作必须写审计日志：

1. 首批真实库样例清理
2. 提示词归档
3. 提示词恢复发布
4. 提示词彻底删除
5. 主分类变更
6. 分类关联变更

每条审计至少记录：

- 操作人
- 操作时间
- 操作对象
- 操作类型
- 变更前摘要
- 变更后摘要
- 执行结果
- 删除或变更原因

对于首批样例清理，建议单独形成一次文档化清理记录，便于后续复核。

## 9. 风险与控制

### 9.1 误删真实资产风险

风险：

- 把仍有业务价值的提示词当作样例删掉

控制：

- 首批清理先导出清单
- 先人工确认再删除
- 清理范围从“明确样例”开始，不做模糊扩删

### 9.2 把归档与删除混用

风险：

- 后台使用者把“下线”误当“删除”，导致资产不可恢复

控制：

- 后台显式区分“归档”和“彻底删除”
- 删除确认文案必须强调不可恢复

### 9.3 分类与主分类失配

风险：

- 多分类调整后主分类指向不存在的关联分类

控制：

- 后端强校验主分类必须属于关联分类
- 前端分类变更时强制重新选择有效主分类

### 9.4 测试基线被误改

风险：

- 把真实库清理动作扩散到 `fixture`/`seed`

控制：

- 方案层面明确禁止
- 本轮仅做真实库治理，不把测试样例同步纳入清理范围

## 10. 实现顺序

本次顺序必须固定，不做并行倒置：

1. 确认真实库待清理样例清单
2. 执行真实库样例彻底删除，并留存审计记录
3. 验证前台与真实库当前正式数据口径稳定
4. 再进入后台提示词管理能力建设
5. 在后台补齐生命周期操作、多分类主分类维护、删除确认与审计展示

这里再次明确：

- 先删真实库样例，再做后台管理能力。
- 不改 `fixture`/`seed` 基线。

## 11. 完成判定

满足以下条件后，视为本设计目标被正确落实：

1. 已形成正式设计文档并冻结为统一基线。
2. 真实库样例清理与后台治理被明确拆成两个阶段。
3. 生命周期语义统一为 `published`、`archived`、彻底删除。
4. 多分类与主分类规则明确，删除分类时的兜底行为明确。
5. 后台交互、权限、审计与风险控制具备可执行口径。
6. `fixture`/`seed` 基线不被纳入本次真实库样例清理。

## 12. 核心结论

本次不是“顺手在后台里加删除按钮”，而是一次顺序明确的数据治理与后台治理拆分：

1. 首先清理真实库样例，直接做彻底删除，不污染正式资产池。
2. 生命周期保持 `published`、`archived`、彻底删除三类结果，各自语义必须分离。
3. 多分类继续保留，但必须补唯一主分类，保证展示、统计与治理口径一致。
4. 后台能力在样例清理之后建设，重点是长期治理，而不是承担首批清库动作。
5. 整个过程不修改 `fixture`/`seed` 基线，确保测试与回归口径稳定。
