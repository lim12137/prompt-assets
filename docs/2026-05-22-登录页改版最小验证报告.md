# 登录页改版最小验证报告（2026-05-22）

## 验证目标

- 仅验证“登录页改版”是否破坏最小核心链路。
- 不修改业务实现文件，仅记录当前可证实结果。

## 当前可用测试入口

- 接口集成：
  - `tests/integration/api/login-auth.test.ts`
- 页面级 E2E：
  - `tests/e2e/smoke/global-auth-header.spec.ts`
  - 其中 `登录成功后回到原页面时右上角立即刷新为已登录态` 最贴近登录页改版后的真实用户路径


## 结果摘要

### 1. 接口集成验证

- 结果：通过，`3 passed / 0 failed`
- 已证实：
  - `POST /api/login -> GET /api/me -> POST /api/logout` 基本链路正常
  - 登录成功后可签发 `auth_token`
  - 登录态可被 `/api/me` 识别
  - 登出可清理 cookie
  - `LOGIN_TOKEN_SECRET` 缺失时仍返回 `500 + auth_configuration_error`

### 2. 页面级最小 E2E 验证

- 结果：未能形成有效页面结论，测试基础设施失败
- 直接现象：
  - 目标用例在等待 `getByPlaceholder("用户名")` 时超时
  - 失败快照显示页面进入 `404`
  - 补跑未登录链路同样失败
- 可确认的阻塞证据：
  - Playwright WebServer 出现大量 `.next-e2e` 构建产物缺失错误
  - 典型报错包括：
    - `ENOENT ... .next-e2e\\routes-manifest.json`
    - `ENOENT ... .next-e2e\\server\\app\\api\\health\\route.js`
    - `ENOENT ... .next-e2e\\server\\vendor-chunks\\...js`
- 判断：
  - 当前失败首先是测试环境/构建产物异常，不能直接判定为“登录页改版功能回归”
  - 但也因此，现阶段还不能用页面级证据证明登录页改版通过

## 最小验证建议

- 若现成 E2E 仍不稳定，最小可证实方案建议按以下顺序执行：
  1. 先保留本次已通过的 `login-auth` 集成测试，作为接口链路证据。
  2. 修复或绕过当前 Playwright `.next-e2e` WebServer 构建异常后，再重跑：

```powershell
pnpm exec playwright test tests/e2e/smoke/global-auth-header.spec.ts --grep "登录成功后回到原页面时右上角立即刷新为已登录态"
```

- 该用例是最小且最贴近改版影响面的页面级验证，因为它直接覆盖：
  - 从详情页点击“登录”
  - 进入 `/login?redirect=...`
  - 提交登录
  - 回跳原页
  - 右上角登录态立即刷新

## 剩余风险

- 当前没有页面级通过证据，因此以下风险仍未被排除：
  - 登录页表单 DOM/文案/占位符是否与现有 E2E 约定一致
  - `/login?redirect=...` 页面路由在真实 E2E WebServer 下是否可正常打开
  - `router.replace(...) + router.refresh()` 的回跳刷新链路是否仍然生效
- 若不先修复 Playwright WebServer 构建异常，任何登录页页面级结论都不够稳固

## 验证结论

- 已证实：登录接口核心链路正常。
- 尚未证实：登录页改版后的页面级交互链路是否正常。
- 当前最准确结论是：接口层通过，页面层验证被 E2E 基础设施故障阻断，不能据此判定改版通过。
